# ogygiaBench — implementation spec

A build-ready spec for finishing `bench/`. It ports **[khromov's interactive-blogs-benchmark](https://github.com/khromov/interactive-blogs-benchmark)**
into this repo on latest tooling, with **ogygia** added. Credit khromov in every user-facing surface
(the README already does). Follow this doc top-to-bottom; each section has acceptance criteria.

---

## 0. The one rule: identical page across frameworks

The benchmark is only valid if **every framework renders the exact same page** — same prose, same
number and placement of interactive widgets, same layout, same CSS. **Only the hydration approach may
differ.** If an app looks or reads differently from the others, the run is void.

Concretely, every app MUST:

- Render the **same three markdown posts** from `bench/posts/{small,medium,large}.md` (generated by
  `generate-posts.mjs` — do not hand-edit; regenerate).
- Contain **exactly 5 `Counter` widgets** per post, at the positions the markdown already places them
  (`<Counter start={N} />`, N = 0,3,6,9,12).
- Use the **shared stylesheet** `bench/shared/post.css` verbatim (link it; do not restyle).
- Produce the **same Counter DOM**: `<button class="bench-counter">count: {n}</button>` that increments
  `n` on click, starting at `start`. Same text, same class, same behavior in every framework.
- Server-render the prose as static HTML. The Counters are the only interactive parts.

The prose is static in all frameworks. The comparison is: **islands ship JS only for the 5 Counters;
whole-page hydration ships JS for the entire document.** That gap is the whole point.

## 3. `frameworks.config.json`

Drives the runner. Each framework entry names how to reach its three post URLs.

```json
{
  "posts": [
    { "id": "small",  "path": "/posts/small",  "words": 8800 },
    { "id": "medium", "path": "/posts/medium", "words": 23000 },
    { "id": "large",  "path": "/posts/large",  "words": 71000 }
  ],
  "frameworks": [
    { "id": "ogygia",    "approach": "islands (svelte 5)",        "dist": "frameworks/ogygia/build" },
    { "id": "sveltekit", "approach": "whole-page (svelte 5)",     "dist": "frameworks/sveltekit/build" },
    { "id": "astro",     "approach": "islands (preact)",          "dist": "frameworks/astro/dist" },
    { "id": "mochi",     "approach": "islands (svelte 5)",        "url": "http://127.0.0.1:3335" }
  ]
}
```

- `dist` = a static/prerendered output the runner serves on an ephemeral port.
- `url` = a pre-running server (mochi builds+serves via bun; started by compose).
- Every app MUST expose the three post paths above. Prerender them where possible so the runner can
  serve a static `dist` (simplest + most reproducible). Mochi may need its own server → use `url`.

**Acceptance:** `curl <framework>/posts/small` returns SSR HTML containing the prose + 5 `bench-counter`
buttons, for all four frameworks.

## 4. `benchmark.ts` (runner — port khromov's methodology exactly)

CLI: `--config <file>` `--posts small,medium,large` `--skip <ids>` `--gzip` `--out <md>` `--json`.

Steps (per the upstream spec):

1. Load config; for each `dist` framework, serve it on `127.0.0.1:0` (ephemeral) with a tiny static
   server (reuse the pattern in `verify/adapters/run.ts`: readFileSync + Content-Length, resolve
   `path` → `path.html` / `path/index.html`). For `url` frameworks, use it directly.
2. Launch headless Chrome (`--no-sandbox`). Pin `Accept-Encoding` for the whole run (`gzip` or
   `identity` per `--gzip`) so every target negotiates the same encoding.
3. Per framework × post:
   - **JS size**: from the Lighthouse/network trace, take every `resourceType === 'Script'` request;
     re-fetch each with `accept-encoding: identity`; sum `raw` (decoded bytes) and `gz` (gzip level 9,
     computed here — independent of how the server served it).
   - **HTML size**: fetch the post URL with `identity`; record raw + gz.
   - **Lighthouse** (mobile emulation + simulated throttling, `categories: ['performance']`,
     `output: 'json'`): extract performance score (0–100), LCP (ms), CLS, TBT (ms), script eval time
     (`bootup-time` audit: Σ scripting + scriptParseCompile), DOM element count (`dom-size`).
4. Average LCP/CLS/TBT/eval/DOM across posts per framework.
5. Emit a markdown table (condensed + full) to `--out` and JSON when `--json`. Warn if content-encoding
   differed across targets (it skews LCP comparability).

Use `lighthouse` (programmatic) + `chrome-launcher`. Sizes via `node:zlib` gzipSync level 9. Keep the
runner dependency-light.

**Acceptance:** `node benchmark.ts --config frameworks.config.json --out results/latest.md --json`
produces a table where, as post length grows, **islands' JS stays ~flat** and **sveltekit's JS grows**.

## 5. Docker (hermetic + reproducible — required)

Astro and some deps pin older Node than this repo uses; Lighthouse needs a real Chrome. Run everything
in one image.

- `Dockerfile`: base `node:22-bookworm` (or `mcr.microsoft.com/playwright` for a bundled Chromium).
  Install pnpm + bun (for mochi). Install Chromium (or use Playwright's). Copy `bench/`. Build all
  framework apps. Default `CMD`: `node generate-posts.mjs && <build all> && node benchmark.ts …`.
- `docker-compose.yml`: one `bench` service that builds the image and runs the benchmark, mounting
  `bench/results/` out so tables land on the host. If mochi needs a long-running server, add a second
  service (or start it in the entrypoint with `PORT=3335 bun run start &`).
- Pin versions in each app's `package.json` (no `^` drift) so the image is reproducible.

**Acceptance:** `docker compose -f bench/docker-compose.yml up --build` runs end-to-end on a clean
machine with only Docker installed, and writes `bench/results/latest.md`.

## 6. The framework apps

All four render the identical page (§0). Below is the per-framework wiring. **Start with 6.1 + 6.2**
(both SvelteKit — they can literally share the Counter + markdown rendering, guaranteeing fidelity),
then 6.3 + 6.4.

### 6.1 `frameworks/ogygia` — Svelte 5 islands (this repo)

- SvelteKit app. Depend on `ogygia` via the packed tarball of this repo's package
  (`pnpm --filter ogygia pack`), NOT a workspace link, so it's the real published shape.
- Wire with `npx ogygia init` (or manually: `ogygia()` in `vite.config` before `sveltekit()`;
  `src/hooks.ts` → `export const transport = ogygia.transport`; `src/hooks.server.ts` →
  `export const handle = ogygia.handle()`).
- `Counter.svelte` = the canonical widget (§0). Import it as an island: `import Counter from
  '$lib/Counter.svelte' with { wake: 'load' }`.
- Post route `src/routes/posts/[slug]/+page.*`: `export const csr = false; export const prerender =
  true;`. Render the markdown (mdsvex or ogygia's `content/markdown`) with `<Counter/>` available.
  Only the 5 Counters hydrate; prose is static.
- Build → `build/` (adapter-static, all posts prerendered). **Expected: JS flat across posts.**

### 6.2 `frameworks/sveltekit` — Svelte 5 whole-page hydration (control)

- Same SvelteKit app, same `Counter.svelte`, same mdsvex rendering, same `post.css` — **byte-identical
  page**. The ONLY difference: no ogygia, and the page hydrates normally (`csr` default true,
  `prerender = true`). Import Counter normally (`import Counter from '$lib/Counter.svelte'`).
- Build → `build/`. **Expected: JS grows with post length** (whole document hydrates).
- To guarantee fidelity, share the Counter + markdown-render component between 6.1 and 6.2 (copy at
  build time from a `bench/shared/svelte/` dir, or a tiny prebuild step). Do not let them drift.

### 6.3 `frameworks/astro` — Preact islands

- Astro app, latest. `@astrojs/preact`. Reimplement `Counter` in Preact so it renders the **same DOM**:
  `<button class="bench-counter">count: {n}</button>`, increment on click, `start` prop. Link
  `post.css`.
- Render the same markdown (Astro content collections / remark) with the 5 Counters as
  `<Counter client:load start={N} />`.
- Build → `dist/`. Islands → flat JS.

### 6.4 `frameworks/mochi` — mochi.fast islands

- Use mochi.fast (Svelte 5 islands + mdsvex). It builds/serves with **bun** (`bun install && bun run
  build && PORT=3335 bun run start`). Reference in config via `url`.
- Same `Counter.svelte`, same markdown, same `post.css`. Mark islands with mochi's directive
  (`mochi:hydrate`).
- Confirm the rendered page matches the others (same prose, 5 counters, same CSS).

## 7. Fidelity check (add as a runner preflight)

Before measuring, assert cross-framework sameness so a drifted app fails loud, not silently:

- Each post URL, across frameworks, must have the **same visible text** (strip scripts/attrs, compare
  normalized prose) and the **same count of `.bench-counter`** (== 5).
- Same `<h1>`/`<h2>` structure. Small diffs in wrapper markup are fine; prose + widget count are not.

Emit `results/fidelity.md` (pass/fail per post) and refuse to publish numbers if it fails.
